# 후기 · 클라이언트 계정 — 나중에 이어서 할 일

작성 2026-11-01 · 관련 마이그레이션 `supabase/migrations/028_reviews.sql`

> **먼저 볼 것 — 028 이 dev DB 에 덜 들어가 있다.**
> 2026-11-01 확인 기준 `reviews` 는 있고 `review_tokens` 는 없다. 중간에 끊긴 듯하다.
> 028 은 멱등하게 썼으니 **대시보드 SQL Editor 에 통째로 다시 붙여 넣고 Run** 하면 된다.
> 맨 아래 확인용 조회가 두 테이블과 RLS 상태를 찍어 준다. 그 전까지 `/review/<token>`
> 은 "유효하지 않은 링크" 로만 나온다.

의뢰는 로그인 없이 받되 후기는 남기게 하려고 만든 구조다. 지금은 **링크로 쓰는
후기**까지만 만들어 두었고, 클라이언트 회원가입은 아직 없다. 나중에 계정을
도입해도 **이미 쌓인 후기를 그 계정에 그대로 이어 붙일 수 있도록** 자리를
비워 두었다. 그 자리가 어디고 어떻게 잇는지를 적어 둔다.

---

## 1. 지금까지 만든 것

**왜 이렇게 했나** — 후기의 신뢰는 "이 사람이 진짜 의뢰했는가"에서 나온다.
계정은 그걸 증명하는 수단 중 하나일 뿐이고, 의뢰 자체가 이미 증명이다.
그래서 그 의뢰에만 쓸 수 있는 1회용 링크를 보내고, 링크를 연 사람을
당사자로 본다. 비회원 의뢰라는 원래 목표를 해치지 않는다.

| 파일 | 역할 |
| --- | --- |
| `supabase/migrations/028_reviews.sql` | `reviews`, `review_tokens` 두 테이블 |
| `src/lib/review-shape.ts` | 타입·길이 상수. 클라이언트도 쓰므로 server-only 아님 |
| `src/lib/reviews-db.ts` | 토큰 확인·발급, 저장, 공개 조회 |
| `src/app/review/[token]/page.tsx` | 작성 화면 (`/review/<uuid>`) |
| `src/app/review/[token]/actions.ts` | 저장 서버 액션 |
| `src/components/review-form.tsx` | 글만 받는 폼 (별점 없음, 10자 이상) |

정해 둔 것:

- **별점 없이 글만** 받는다. 별점을 함께 받으면 글은 안 쓰고 별만 누르고 나간다.
- **승인 후 공개**. 작성 직후 `status = 'pending'` 이라 공개 화면에 안 뜬다.
- **의뢰 1건 = 후기 1개** (`reviews.inquiry_id` unique).
- 작성자 이름은 공개 화면에서 `김*연` 으로 가린다(`maskName`). 이메일은 안 나간다.

## 2. 아직 안 만든 것

아래 함수들은 `reviews-db.ts` 에 **있지만 아무 데서도 호출하지 않는다.**
화면을 붙이면 바로 쓸 수 있다.

### 2-1. 링크 발송 (가장 먼저 할 일)

지금은 링크를 만들 방법이 화면에 없다. 손으로 DB에 토큰을 넣어야 열린다.

- `ensureReviewToken(inquiryId)` — 토큰을 가져오거나 없으면 만든다.
  한 의뢰에 토큰은 **하나만** 둔다. 보낼 때마다 새로 만들면 먼저 받은 링크가
  조용히 죽어 "눌렀더니 안 돼요" 가 된다. 기간만 지났으면 토큰은 그대로 두고
  `expires_at` 만 늘린다.
- `markReviewLinkSent(token)` — 보낸 횟수를 센다.

붙일 자리: 어드민 문의 상세(`src/app/admin/inquiries`)에 **"후기 요청 보내기"**
버튼. 누르면 토큰을 만들고 메일을 보낸다.

메일은 `src/lib/designer-mail.ts` 의 `sendTempPassword` 와 같은 모양으로
`sendReviewRequest` 를 추가하면 된다 — Resend 는 이미 붙어 있다.

보낼 주소: `${NEXT_PUBLIC_SITE_URL}/review/${token}`

### 2-2. 어드민 승인 화면

`status = 'pending'` 인 후기가 쌓이기만 하고 공개할 방법이 없다.

- `listReviews(status?)` — 목록
- `countPendingReviews()` — 사이드바 배지용

붙일 자리: `/admin/reviews`. 승인·반려 버튼과 반려 사유(`status_memo`).
사이드바는 `src/app/admin/layout.tsx`.

### 2-3. 공개 화면에 후기 붙이기

- `listDesignerReviews(designerId)` — 승인된 것만, 이메일은 떼고 돌려준다.

붙일 자리: 디자이너 상세(`src/app/designers/[id]`).

## 3. 카카오 알림톡으로도 보내려면

이메일은 지금 바로 되지만 카카오는 준비물이 있다.

- **사업자등록증 + 카카오 비즈니스 채널 + 발신프로필**
- **템플릿 사전 심사** (1~3영업일). 광고가 아닌 **정보성 메시지만** 통과한다.
  "후기를 남겨주세요" 는 반려될 수 있어, **작업 완료 안내**를 본문으로 하고
  후기 링크를 부가로 붙이는 형태로 올린다.
- 비용 건당 7~15원. 대행사는 솔라피·알리고·NHN Toast 등.
- **대체발송(LMS)** 을 꼭 켠다 — 채널 미가입·차단이면 문자로 넘어간다.
- 알림톡은 **휴대폰 번호가 필수**다. `inquiries.phone` 은 이미 있다
  (013_inquiry_phone.sql). 다만 **nullable** 이라 안 적고 보낸 의뢰가 있을 수 있으니,
  번호가 없으면 메일로만 보내는 분기가 필요하다.

발송 로직을 `sendReviewLink(inquiry)` 하나로 감싸 두면, 안에서 채널만 늘리면 된다.
이메일 먼저 붙이고 알림톡은 심사 끝난 뒤 얹는 순서를 권한다.

## 4. 클라이언트 회원가입이 생겼을 때

### 4-1. 연결 고리는 `author_email`

`reviews.author_email` 에 **작성 시점의 이메일을 박아 둔다.** 의뢰 쪽 값을
참조하지 않고 베껴 둔 이유는, 의뢰가 나중에 고쳐져도 후기에 쓰인 신원은
그대로여야 하기 때문이다. 이 값이 나중에 계정과 잇는 열쇠다.

가입 시 이렇게 잇는다:

```sql
update public.reviews
   set client_id = $1, linked_at = now()
 where client_id is null
   and lower(author_email) = lower($2);
```

`reviews_unlinked_idx` 가 `lower(author_email)` 에 `where client_id is null` 로
걸려 있어 이 조회는 빠르다.

`inquiries` 도 같은 방식으로 이으면, 가입하자마자 **"내 의뢰 내역 + 내가 쓴 후기"**
가 한 번에 보인다. 이게 가입 유인이 된다 — 가입을 강요하지 않고도 가입하게 만드는 쪽.

### 4-2. 해야 할 일

1. `clients` 테이블 추가
2. `reviews.client_id` 에 외래키 추가 — 지금은 `clients` 가 없어서 안 걸어 두었다
   ```sql
   alter table public.reviews
     add constraint reviews_client_fk
     foreign key (client_id) references public.clients(id) on delete set null;
   ```
   `on delete set null` 이어야 한다. 계정을 지워도 후기는 남아야 한다.
3. 가입 직후 위 update 를 돌리는 로직

### 4-3. 인증 방식

디자이너 로그인(`src/lib/designer-auth.ts`)이 **자체 JWT 를 httpOnly 쿠키**에
담는 방식이다. 클라이언트도 같은 패턴(`client-auth.ts`)으로 가는 쪽을 권한다 —
Supabase Auth 의 카카오 Provider 를 쓰면 세션이 Supabase 것이 되어 인증 체계가
두 벌이 된다. 어드민만 Supabase Auth(구글)를 쓰는데 그건 어드민 전용 예외다.

카카오 OAuth 직접 붙이기:

- 카카오 개발자센터에서 `KAKAO_CLIENT_ID`(REST API 키), `KAKAO_CLIENT_SECRET`
- **Redirect URI 는 콘솔에 등록**해야 한다(환경변수가 아니다)
- **동의항목**(이메일·닉네임·프로필 이미지)도 콘솔에서 켠다
- 라우트 `/auth/kakao` → `/auth/kakao/callback`, 받은 신원으로 `createSession()`

**주의**: 카카오는 **이메일 제공이 선택 동의**라 거부하면 이메일이 안 온다.
위 4-1 연결이 이메일 기준이라 이 경우를 처리해야 한다 — 휴대폰으로 잇거나,
가입 시 이메일을 따로 묻거나.

### 4-4. 가입을 권하는 자리

의뢰 플로우에서는 가입을 **권하지 않는다.** 비회원 의뢰를 만든 의미가 사라진다.

| | 자리 |
| --- | --- |
| 좋음 | 의뢰 완료 화면, 후기 작성 완료 후, 비회원 의뢰 조회 페이지 하단 |
| 나쁨 | 의뢰 폼 시작 전·중간, 모달로 띄우기 |

## 5. 포트폴리오와 잇기 (더 나중)

`reviews.work_id` 를 비워 두었다. 외래키는 **걸지 않았다** — 작업이 지워져도
후기는 남아야 한다.

디자이너가 작업을 올릴 때 **"SOOM에서 수행한 의뢰"**(`designer_works.soom_work`,
020 마이그레이션)를 켜면, 그 작업이 어떤 의뢰의 결과물인지 고르게 한다.
그 값을 `reviews.work_id` 에 담으면 포트폴리오 카드 밑에 그 일을 맡긴 사람의
후기를 붙일 수 있다.

조회는 `reviews_work_idx` (`where work_id is not null`) 가 받는다.

지금은 **자리만 있고 아무것도 채우지 않는다.**

## 6. 외래키를 안 건 자리 (의도된 것)

실수로 보고 FK 를 추가하지 말 것. `designer_works`·`inquiries` 와 같은 방침이다.

| 컬럼 | FK 없음 이유 |
| --- | --- |
| `reviews.designer_id` | 디자이너가 지워져도 후기·평판은 남아야 한다. 대신 `designer_name` 을 함께 박아 둬 계정이 사라져도 누구 얘기인지 남는다 |
| `reviews.work_id` | 작업이 지워져도 후기는 남아야 한다 |
| `reviews.client_id` | `clients` 테이블이 아직 없다. 생기면 `on delete set null` 로 건다 |

반대로 **FK 를 건 자리**는 지워져야 맞는 것들이다:

- `reviews.inquiry_id` → `on delete cascade`. 무엇에 대한 후기인지 알 수 없는
  글만 남기느니 지우는 편이 낫다.
- `review_tokens.inquiry_id` → `on delete cascade`. 어디에도 닿지 않는 죽은 링크.
